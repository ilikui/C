# 54｜模块集成、接口契约与故障传播

## 学习目标

- 把模块接口从“函数声明”提升为可验证的行为契约。
- 统一错误码、超时语义和资源所有权。
- 在集成测试中检查故障是否被正确传播，而不是被吞掉或重复处理。

## 1. 契约包含哪些内容

一个可集成的接口至少应明确：

1. 参数范围、单位、允许的空指针及缓冲区长度。
2. 成功时输出如何更新；失败时输出是否保持不变。
3. 错误码定义、错误是否可重试、重试次数和退避策略。
4. 执行上下文、并发限制、是否可重入。
5. 超时单位、时间源、超时后的资源清理。
6. 数据所有权、生命周期和有效期。
7. 接口版本与兼容性要求。

## 2. 故障传播链

```mermaid
flowchart LR
    HW["硬件/驱动错误"] --> ADP["平台适配层映射错误"]
    ADP --> SVC["服务层保留错误语义"]
    SVC --> APP["应用层选择降级/重试/停止"]
    APP --> OBS["诊断事件与可追溯记录"]
```

每一层可以增加上下文，但不应将“读取失败”改写成“读取成功且值为 0”。错误映射应保留足够信息供上层决策。

## 3. 返回值与输出参数约定

```c
#include <stdint.h>

typedef enum {
    STATUS_OK = 0,
    STATUS_INVALID_ARGUMENT,
    STATUS_IO_ERROR,
    STATUS_TIMEOUT,
    STATUS_NOT_READY
} status_t;

/*
 * 契约：
 * - out_value 必须非空。
 * - 成功时写入结果。
 * - 失败时不修改 *out_value。
 */
status_t service_get_value(int32_t *out_value);
```

失败时是否修改输出参数必须明确。可采用“成功才写入”的约定，让调用者不会把部分结果误认为有效结果；若项目采用其他策略，也必须统一说明。

## 4. 集成测试矩阵

| 场景 | 注入点 | 期望结果 |
|---|---|---|
| 底层 I/O 错误 | Fake 驱动 | 服务返回对应错误，上层执行规定策略 |
| 超时 | 虚拟时钟或延迟响应 | 在预算内结束，不无限等待 |
| 参数非法 | 公共 API | 返回参数错误，不发生副作用 |
| 重复调用 | 服务 API | 状态保持一致，无资源重复分配 |
| 恢复成功 | 故障解除后 | 按契约恢复，不遗留旧故障状态 |
| 多错误同时发生 | 多个 Fake 输入 | 优先级和故障覆盖规则可解释 |

## 5. 版本与兼容性

- 对外结构体布局一旦成为 ABI 的一部分，就要审查字段新增、对齐和编译器差异。
- 优先通过不透明句柄隐藏私有状态；若使用公共结构体，应明确版本策略。
- 函数签名、错误码和单位变化属于接口变更，应同步更新调用方和测试。
- 不能仅依赖“编译通过”证明兼容；还需检查行为、链接和目标平台约束。

## 6. 练习与验收

1. 选一个模块，补齐成功、失败、超时和并发契约。
2. 为每个错误码写出上层处理策略。
3. 使用 Fake 驱动验证错误从底层传到应用层的完整路径。
4. 模拟接口新增字段或错误码，完成兼容性审查记录。

**验收标准：** 接口契约可被测试用例逐条验证；错误不会被静默吞掉；输出参数和资源清理行为在成功与失败路径上均明确。
