# 25. 单元测试、边界测试与静态分析

## 学习目标
- 将纯逻辑从硬件依赖中隔离，便于快速验证。
- 使用边界值、故障注入和状态覆盖发现问题。
- 把编译警告、静态分析和测试纳入日常开发流程。

## 验证金字塔
~~~mermaid
flowchart TD
    A["静态检查：格式 / 警告 / 分析"] --> B["单元测试：纯逻辑与边界"]
    B --> C["模块集成测试：接口与依赖"]
    C --> D["目标板测试：时序 / 外设 / 中断"]
    D --> E["回归测试：每次修改后重跑"]
~~~

## 1. 可测试函数的特点
- 输入与输出明确。
- 尽量减少全局状态。
- 硬件操作通过接口注入或隔离。
- 错误路径有明确返回值。
- 时间、随机数和外设结果可以在测试中控制。

例如对数值换算、报文解析、状态机转移和环形缓冲区，优先测试纯 C 逻辑；不要把所有逻辑都包在只能运行于目标板的函数中。

## 2. 边界测试清单
| 对象 | 最少覆盖 |
|---|---|
| 数组/缓冲区 | 长度为 0、最小合法长度、最大容量、超长输入 |
| 数值换算 | 最小值、最大值、零、负值、溢出附近 |
| 状态机 | 每条合法转移、每类非法事件、故障恢复 |
| 文件/报文解析 | 空输入、截断数据、格式错误、正常输入 |
| 动态内存 | 分配失败、零长度约定、释放路径、重复清理 |
| 环形队列 | 空、满、回绕、长时间反复读写 |

## 3. 本地编译检查
对可移植的 C11 单元测试，可从严格警告开始：

~~~sh
cc -std=c11 -Wall -Wextra -Wpedantic -Wconversion -Wshadow test.c module.c -o test
~~~

工具链支持时，可以在独立的主机测试构建中启用 AddressSanitizer 或 UndefinedBehaviorSanitizer。它们不能替代目标板测试，也无法证明实时性、硬件时序或并发设计一定正确。

## 4. 缺陷闭环
~~~mermaid
flowchart LR
    A["复现问题"] --> B["缩小到最小案例"]
    B --> C["增加回归测试"]
    C --> D["修复实现"]
    D --> E["运行相关测试"]
    E --> F{"测试通过？"}
    F -- "否" --> B
    F -- "是" --> G["记录原因与预防措施"]
~~~

## 练习与验收
1. 为前面章节中的位操作、定点换算、状态机和环形队列编写测试。
2. 对每个输入参数设计正常、边界和非法输入。
3. 为错误返回路径注入失败条件。
4. 将编译警告和测试命令写入项目 README 或构建脚本。

**验收标准：** 核心逻辑能在主机独立测试；边界和故障路径有测试；每次修复都有回归验证；明确区分主机测试与目标板验证。
