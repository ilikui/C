# 24. 错误码、断言、日志与故障诊断

## 学习目标
- 区分可预期的运行时错误与程序不变量被破坏。
- 设计一致的错误传播方式。
- 让日志在嵌入式资源约束下仍然可用、可定位。

## 错误处理路径
~~~mermaid
flowchart TD
    A["调用模块接口"] --> B{"输入和状态有效？"}
    B -- "否" --> C["返回参数/状态错误"]
    B -- "是" --> D["执行操作"]
    D --> E{"操作成功？"}
    E -- "是" --> F["返回成功"]
    E -- "否" --> G["记录上下文并传播错误"]
    G --> H["恢复 / 降级 / 安全状态"]
~~~

## 1. 用枚举表达错误语义
~~~c
typedef enum {
    APP_OK = 0,
    APP_ERR_ARGUMENT,
    APP_ERR_NOT_INITIALIZED,
    APP_ERR_TIMEOUT,
    APP_ERR_HARDWARE,
    APP_ERR_OUT_OF_RANGE
} app_status_t;
~~~

错误码应代表调用者能够采取不同处理动作的类别。不要为了“看起来详细”创建大量无法区分处理方式的错误码，也不要把错误码与合法业务数据混用。

## 2. 断言的使用边界
断言适合验证开发期不变量，例如内部函数要求某个指针必须非空。来自外部报文、用户输入、传感器或硬件的异常属于运行时情况，通常应通过错误返回处理，而不是依赖断言。

~~~c
#include <stdbool.h>
#include <stddef.h>

static bool copy_value(const int *source, int *destination)
{
    if (source == NULL || destination == NULL) {
        return false;
    }

    *destination = *source;
    return true;
}
~~~

此处使用运行时检查，因为参数可能来自调用边界。断言是否启用、失败后如何处理，需由构建配置和安全需求决定。

## 3. 嵌入式日志的工程约束
- 为日志定义等级：错误、警告、信息、调试。
- 记录模块、事件编号、状态和关键参数；避免输出敏感数据。
- ISR 中避免调用阻塞式或不可重入日志接口。
- 高频路径考虑计数器、事件缓冲区或采样日志，防止日志改变实时行为。
- 日志写入失败不能造成二次故障；明确缓冲区满时的策略。
- 对时间戳、复位原因和故障快照建立统一格式。

## 4. 错误传播原则
函数检测到错误后，应决定是立即返回、清理资源后返回、尝试恢复，还是将系统切换到安全状态。不要捕获错误后无记录地继续运行，也不要在清理路径中覆盖最初的错误原因。

## 练习与验收
1. 为驱动定义错误码并写出调用者的处理表。
2. 设计一个不会在 ISR 中阻塞的故障记录机制。
3. 区分适合断言的内部不变量和必须返回错误的外部输入。
4. 测试超时、硬件失败和资源不足路径。

**验收标准：** 错误语义统一；错误能够被追踪；异常输入不会依赖断言处理；日志不会破坏关键时序。
