# 23. 驱动接口、硬件抽象层与依赖隔离

## 学习目标
- 将业务逻辑与寄存器、RTOS 和芯片细节分离。
- 设计可替换、可测试的驱动接口。
- 明确初始化顺序、资源所有权和错误传播。

## 分层关系

## 1. 定义小而清晰的接口
~~~c
#ifndef SENSOR_PORT_H
#define SENSOR_PORT_H

#include <stdbool.h>
#include <stdint.h>

typedef struct {
    int32_t milli_units;
} sensor_sample_t;

/* 成功返回 true 并写入 sample；失败时 sample 内容不作保证。 */
bool sensor_port_read(sensor_sample_t *sample);

#endif
~~~

业务层只依赖 sensor_port_read，不需要知道 ADC 通道号、寄存器地址或 DMA 缓冲区。实现文件负责检查空指针、调用底层驱动、处理硬件错误，并将原始值转换为接口约定的单位。

## 2. 错误必须有明确语义
单纯返回一个数值，容易把“真实测量值为 0”和“读取失败”混在一起。可以采用布尔返回值加输出参数、枚举错误码，或项目已有的 Result 类型。选择后要在整个项目保持一致。

## 3. 初始化与生命周期
~~~mermaid
sequenceDiagram
    participant App as 应用
    participant Svc as 传感器服务
    participant Port as 硬件接口
    participant HW as 外设
    App->>Svc: init()
    Svc->>Port: configure()
    Port->>HW: 配置时钟/引脚/ADC
    HW-->>Port: 状态
    Port-->>Svc: 成功或错误
    Svc-->>App: 初始化结果
    App->>Svc: read()
    Svc->>Port: 读取样本
    Port-->>Svc: 样本或错误
~~~

应明确谁负责初始化和关闭外设；初始化失败后能否重试；调用 read 前是否必须 init；中断回调是否可能早于服务准备完成。

## 常见错误
- 业务逻辑直接读写多个寄存器，导致难以测试。
- 返回值不区分合法零值和失败。
- 头文件泄露不必要的硬件实现细节。
- 多个模块重复配置同一个外设。
- 初始化失败后仍继续使用未初始化的句柄或缓冲区。

## 练习与验收
1. 为 ADC 或温度传感器设计接口头文件。
2. 写一个 fake 实现，能返回正常值、边界值和故障。
3. 让业务算法在不连接真实 MCU 的情况下运行单元测试。
4. 画出初始化依赖顺序并列出失败回滚策略。

**验收标准：** 业务层不依赖具体寄存器；接口错误语义清晰；硬件实现可被测试替身替换。
