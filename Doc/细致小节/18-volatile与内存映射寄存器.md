# 18. volatile 与内存映射寄存器

## 学习目标

- 理解 volatile 对编译器访问行为的约束，以及它的能力边界。
- 知道硬件寄存器访问必须遵循芯片手册、编译器和平台 ABI。
- 不把 volatile 当作原子操作、线程同步或通用内存屏障。

## 概念关系

~~~mermaid

    A["硬件 / 外部异步可见状态"] --> B["平台定义的寄存器访问"]

    E["多线程 / 中断共享数据"] --> F["原子、临界区或平台同步机制"]
    C -. "不能替代" .-> F
~~~

## 1. volatile 的含义和边界

volatile 用于告诉实现：对该对象的访问具有可观察性，不能像普通无可观察副作用的访问那样任意消除或合并。它**不保证**：

- 操作是原子的；
- 多线程之间建立同步关系；
- 普通内存访问与硬件访问具有所有平台都一致的顺序；
- 复合表达式不会被中断；
- 任意地址都是真实有效的硬件寄存器。

## 2. 内存映射寄存器示例（仅示意）

~~~c
#include <stdint.h>

/*
 * 仅示意：真实地址、访问宽度、对齐和寄存器语义必须查芯片手册。
 * 某些寄存器有读清零、写 1 清零或保留位规则，不能随意读改写。
 */
#define PERIPHERAL_STATUS (*(volatile uint32_t *)PERIPHERAL_STATUS_ADDRESS)

static uint32_t read_status(void)
{
    return PERIPHERAL_STATUS;
}
~~~

该示例不是可直接运行的通用代码。实际项目必须由平台头文件或供应商 CMSIS/设备头文件提供正确地址和类型；不要凭空定义寄存器地址。寄存器访问宽度和读写副作用以芯片文档为准。

## 3. 中断共享标志位

例如 ISR 更新一个标志、主循环读取该标志时，volatile 在部分嵌入式编译器约定中用于确保每次访问都实际发生，但是否足够取决于目标平台与编译器文档。若涉及多个字段、一致性快照、读改写、计数器或多核同步，需要进一步设计：

- 使用平台规定的原子操作；
- 或在读写共享状态时使用适当的中断屏蔽/临界区；
- 由驱动和 RTOS 明确同步契约；
- 评估原子类型是否可在 ISR 上下文安全使用。标准 C 原子设施并不自动保证适用于所有中断环境。

## 4. 读改写风险

~~~c
volatile unsigned int flags;

/* flags |= MASK; 可能是读、修改、写的多个步骤，不保证原子。 */
~~~

若 ISR 与主循环同时修改 flags，更新可能互相覆盖。不要因为变量声明为 volatile 就认为竞争已经解决。

## 练习与验收

1. 从目标 MCU 手册中找出一个状态寄存器，记录地址、访问宽度和读取副作用。
2. 解释 volatile 与 atomic 的区别。
3. 给一个 ISR/主循环共享状态设计同步方案，并注明编译器、CPU、RTOS 的平台假设。
4. 检查工程中是否存在对硬件寄存器进行不合规读改写的代码。

**验收标准：** 能说明 volatile 的作用范围；寄存器定义有真实平台依据；共享数据同步方案不单靠 volatile。
