# 27. 编译期配置、条件编译与可移植性

## 学习目标
- 区分标准 C、编译器扩展和平台相关代码。
- 使用配置宏控制功能，而不是在代码中散落魔法值。
- 避免条件编译造成接口不一致或配置组合失控。

## 配置决策流程
~~~mermaid
flowchart TD
    A["新需求或平台差异"] --> B{"标准 C 能否满足？"}
    B -- "能" --> C["优先使用标准写法"]
    B -- "不能" --> D["封装平台适配层"]
    C --> E["集中定义配置"]
    D --> E
    E --> F["检查所有配置组合"]
    F --> G["编译与测试"]
~~~

## 1. 集中管理配置
~~~c
#ifndef APP_CONFIG_H
#define APP_CONFIG_H

#define APP_ENABLE_DIAGNOSTICS 1
#define APP_MAX_MESSAGE_SIZE 128U

#if (APP_ENABLE_DIAGNOSTICS != 0) && (APP_ENABLE_DIAGNOSTICS != 1)
#error "APP_ENABLE_DIAGNOSTICS must be 0 or 1"
#endif

#if APP_MAX_MESSAGE_SIZE < 8U
#error "APP_MAX_MESSAGE_SIZE is too small"
#endif

#endif
~~~

宏的合法性检查应考虑预处理器表达式规则，复杂类型检查通常留给 C 编译器。配置值应集中放在一个位置，并记录允许范围和相互依赖关系。

## 2. 隔离平台差异
~~~c
#ifndef TICK_PORT_H
#define TICK_PORT_H

#include <stdint.h>

/* 由目标平台提供实现。 */
uint32_t tick_port_now(void);

#endif
~~~

业务逻辑只依赖接口，不直接读取某个 MCU 的定时器寄存器。不同平台分别提供实现，避免在业务代码里充斥芯片型号宏。

## 3. 可移植性检查
- 使用 stdint.h 中的定宽整数类型表达明确位宽需求，但注意精确宽度类型在少数实现上可能不存在。
- 不假定 int 一定为 32 位，也不假定字节一定为 8 位；协议若定义 octet，应明确平台前提。
- 不把结构体内存布局直接当作跨平台文件或网络协议格式。
- 对编译器扩展、内联汇编、链接脚本和内存映射寄存器注明目标工具链。
- 检查宏参数是否会被多次求值；优先用类型安全的函数替代复杂宏。

## 练习与验收
1. 将项目中的平台宏集中到配置层。
2. 为主机模拟和目标板实现同一个端口接口。
3. 列出项目使用的编译器扩展与平台假设。
4. 为两个配置组合分别编译，确保公共接口不发生意外变化。

**验收标准：** 平台差异集中封装；配置有范围和依赖说明；标准写法与扩展写法有明确区分。
